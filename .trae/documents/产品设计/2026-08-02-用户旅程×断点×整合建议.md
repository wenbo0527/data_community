# 用户旅程 × 断点 × 整合建议

> **版本**: v1.0
> **日期**: 2026-08-02
> **视角**: 用户体验(User Experience)
> **前置**: 已完成 [数据流分析](./2026-08-02-三大模块整合-数据流与应用流分析.md) + [整合方案 v1.0](./2026-08-02-三大模块代码整合方案.md)
> **目标**: 从用户实际操作出发,识别"断点",而不是从代码层面看 —— 真正的整合障碍往往在 UX

---

## 0 · TL;DR

三个模块的代码整合(L1-L4)已经做了。但**用户旅程层面**仍有 **6 大类 22 个断点**:

| 类别 | 数量 | 严重度 |
|:---|:---:|:---:|
| 🔴 上下文丢失 | 5 | 阻断 |
| 🟠 信息分裂 | 6 | 影响效率 |
| 🟡 操作割裂 | 5 | 增加成本 |
| 🟢 一致性 | 3 | 影响体验 |
| ⚪ 边界认知 | 3 | 影响信任 |

**核心矛盾**: 用户视角是"我要完成一件事",产品视角是"我在哪个模块"。

---

## 1 · 用户角色画像

| 角色 | 工作目标 | 在平台主要做的事 |
|:---|:---|:---|
| **📊 数据分析师** (Analyst) | 用数据回答业务问题 | 找数据 → 探查 → 写 SQL/建模 → 出报告 |
| **🏷️ 业务运营** (Operator) | 用数据圈选人群、做活动 | 看标签 → 圈人群 → 申请外数 → 触达 |
| **🛡️ 数据治理** (Steward) | 维护数据资产质量 | 上架资产 → 维护标准 → 配置权限 |
| **🧑‍💼 业务决策者** (Executive) | 看指标做决策 | 看仪表盘 → 钻取 → 看 360 |

> **关键观察**: 一个用户常常跨越多个角色。例如分析师也需要申请权限,治理者也需要看指标。

## 2 · 5 个典型用户旅程(端到端)

### 🟢 旅程 A:**"我想知道某客户的总授信额度"**(最常见)

```
业务决策者视角:
1. 打开平台首页
2. 进入"数据探索"工作台
3. 搜索"客户授信"
4. → 应该出现什么?
5. 拿到数据,关闭页面
```

### 🟢 旅程 B:**"我需要申请一个外数指标"**(跨模块典型)

```
数据分析师视角:
1. 在数据探索的"指标看板"里,看到外数指标 X
2. 想了解 X 怎么定义的
3. → 跳到"数据发现"看指标详情
4. → 再跳到"数据管理"申请使用
5. → 审批通过后回来使用
```

### 🟢 旅程 C:**"我圈选了一个人群,想保存成客户 360 标签"**(跨产品典型)

```
业务运营视角:
1. 在"数据探索-客群中心"圈选人群
2. 想把人圈选结果"固化成标签"
3. → 跳到标签体系创建标签
4. → 把圈选规则作为标签规则
5. → 然后在"客户 360"里看到
```

### 🟢 旅程 D:**"我发现一个表数据有问题,要找人修"**(治理典型)

```
数据分析师视角:
1. 在"数据发现-数据地图"看到表 A
2. 钻到表详情发现数据脏
3. → 发起"质量工单"
4. → 跳到"数据管理-元数据采集"给 Owner 提工单
5. → Owner 在管理端处理
```

### 🟢 旅程 E:**"我做了一份分析,想分享给同事"**(协作典型)

```
数据分析师视角:
1. 在"数据探索-分析流程"做了一份分析
2. 想分享给运营同事
3. → 发布成看板
4. → 在"客户 360"里嵌入
```

## 3 · 旅程 × 断点 × 整合建议

### 🚦 旅程 A:看客户授信额度

#### 当前实际步骤(推断)

| 步骤 | 用户动作 | 进入页面 | 模块 | 状态 |
|:---:|:---|:---|:---|:---:|
| 1 | 登录 | `/login` | - | ✅ |
| 2 | 看到工作台 | `/discovery/index` (UnifiedWorkbench) | discovery | ✅ |
| 3 | 搜索"客户授信" | `/discovery/index` (顶部 search) | discovery | ✅ 接 search-api |
| 4 | 看到搜索结果:tables + metrics + concepts | (Drawer) | discovery | ✅ |
| 5 | 点击"指标"卡片 | → ??? | ??? | 🔴 |
| 6 | 看到 customer360 详情 | `/discovery/customer360/detail/...` | discovery | ⚠️ |

#### 🔴 断点 A-1:**搜索结果 → 跳转目标模糊**

| 问题 | 严重度 | 证据 |
|:---|:---:|:---|
| 搜索"客户授信"返回的"指标"卡,点击后跳到 `discovery:metrics-map`,但**用户想看的是客户层数据** | 🔴 | 路由 `metrics-map` 是指标字典,不是客户数据 |

**整合建议**:
- 搜索结果按**用户意图**分类,而不是按数据类型
- 增加"客户洞察"分类,跳转 `customer360` + 预填搜索条件

---

#### 🔴 断点 A-2:**指标 → 客户数据 的鸿沟**

| 问题 | 严重度 | 证据 |
|:---|:---:|:---|
| 用户在 metrics-map 看到"客户授信总额"指标,但想看**单个客户的授信** | 🔴 | 当前无"从指标到 360"的快捷入口 |

**整合建议**:
- 指标详情页增加"查看关联客户"按钮,跳转到预过滤的 customer360 列表

---

### 🚦 旅程 B:申请外数指标

#### 当前实际步骤

| 步骤 | 用户动作 | 进入页面 | 模块 |
|:---:|:---|:---|:---|
| 1 | 看指标看板 | `/exploration/indicator-dashboard` | exploration |
| 2 | 看到外数指标 X,点详情 | (Drawer) | exploration |
| 3 | 想看指标定义 → 跳数据发现 | `discovery:metrics-map` | discovery |
| 4 | 跳到管理申请 → | `management:service` | management |
| 5 | 填工单 | (内页表单) | management |
| 6 | 审批完成 → 回到探索用 | `exploration:indicator-dashboard` | exploration |

#### 🟠 断点 B-1:**指标 schema 在三处不一致**

| 位置 | 字段差异 |
|:---|:---|
| exploration/indicator-dashboard | 用 `definition` + `businessOwner` |
| discovery/metrics-map | 用 `businessDefinition` + `owner` |
| management/metric-management | 用 `definition` + `metricOwner` |

| 问题 | 严重度 |
|:---|:---:|
| 用户在 A 处看到"日活 100 万",跳到 B 处看到"日活 95 万" —— **数字对不上** | 🟠 |

**整合建议**:
- 统一 `Metric` schema(已在 L1 方案中标记 P1)
- 跨模块跳转时,**带上当前指标 ID**,目标模块自动定位同一指标

---

#### 🟠 断点 B-2:**外数申请 → 审批状态不同步**

| 问题 | 严重度 |
|:---|:---:|
| 用户提交申请后,在 exploration 看不到审批状态,需要切回 management 查 | 🟠 |

**整合建议**:
- 在 exploration 工作台顶部"我的申请"卡片实时显示审批进度

---

#### 🟡 断点 B-3:**指标详情 → 申请的路径长**

当前:`详情页 → 跳数据发现 → 跳数据管理 → 找服务申请 → 选指标`

**整合建议**:
- 指标详情页直接嵌入"申请使用"按钮,无需跨页

---

### 🚦 旅程 C:人群圈选 → 标签固化

#### 🔴 断点 C-1:**标签(管理)与人群(探索)的概念模糊**

| 位置 | 概念 |
|:---|:---|
| exploration/audience-system | "人群"(Crowed) |
| exploration/tag-system | "标签"(Tag) |
| management/tag-management | "标签组" |

| 问题 | 严重度 |
|:---|:---:|
| 用户分不清"标签"和"人群"区别,以为是一回事 | 🔴 |

**整合建议**:
- 引入概念文档:标签=用户属性(BOOL/枚举);人群=符合规则的用户集合
- UI 上明确标注

---

#### 🔴 断点 C-2:**圈选 → 固化标签的入口缺失**

| 问题 | 严重度 |
|:---|:---:|
| exploration 圈选完人群后,**没有"固化成标签"按钮** | 🔴 |

**整合建议**:
- 圈选结果页增加"保存为标签"按钮 → 跳到 tag-system 表单,自动填充圈选规则

---

### 🚦 旅程 D:数据质量工单

#### 🟠 断点 D-1:**元数据采集 vs 数据地图的"表"是同一个吗?**

| 位置 | mock 数据 |
|:---|:---|
| management/metadata-collection | 表列表来自 `metadata-api.ts`(Mock) |
| discovery/data-map | 表列表来自 `metadata-store.ts`(MetadataStore) |

| 问题 | 严重度 |
|:---|:---:|
| 用户在 A 处提工单针对"表 X",在 B 处看不到对应工单状态 | 🟠 |

**整合建议**:
- 统一数据底座(已部分接入 MetadataStore,深度整合需进一步)
- 在 data-map 表详情页直接显示"工单状态"

---

#### 🟡 断点 D-2:**Owner 信息不同步**

| 问题 | 严重度 |
|:---|:---:|
| metadata-collection 显示 Owner 是"张三",data-map 显示 Owner 是"李四" | 🟡 |

**整合建议**:
- Owner 也走共享底座

---

### 🚦 旅程 E:分析 → 分享

#### 🟢 断点 E-1:**分析结果输出位置分散**

| 类型 | 输出位置 |
|:---|:---|
| SQL 查询 | 临时页面,无法保存 |
| 看板 | indicator-dashboard |
| Jupyter | 独立环境 |
| 工作流 | workflows 内部 |

| 问题 | 严重度 |
|:---|:---:|
| 用户做完分析,**找不到统一"我的产出"** | 🟢 |

**整合建议**:
- 增加"我的产出"统一视图(在工作台)

## 4 · 横向断点盘点

### 4.1 上下文丢失类(5 个)

| # | 断点 | 触发场景 |
|:---:|:---|:---|
| 1 | 跨模块跳转不带筛选条件 | 用户在 A 模块应用了筛选,跳到 B 模块时筛选丢失 |
| 2 | 选中项丢失 | 在 A 模块选中 1 个表,跳到 B 模块编辑时未自动选中 |
| 3 | 搜索词不传递 | 工作台搜索"客户授信"跳到结果页,结果页 input 是空的 |
| 4 | 时间范围不传递 | 看板看"近 7 天"切到明细查询时变成"全部" |
| 5 | 登录态/角色丢失 | (理论上不会,实际已修) |

### 4.2 信息分裂类(6 个)

| # | 断点 | 表现 |
|:---:|:---|:---|
| 1 | Owner 多版本 | 不同模块同一表 Owner 不一样 |
| 2 | 指标定义多版本 | exploration/management/discovery 三套 schema |
| 3 | 标签 vs 人群 概念混淆 | 用户分不清 |
| 4 | 字段权限 vs 数据标准 | 维度概念不同源 |
| 5 | 血缘散落 | lineage 单独模块,其他模块看不到 |
| 6 | 数据质量分散 | 各模块独立计分 |

### 4.3 操作割裂类(5 个)

| # | 断点 | 表现 |
|:---:|:---|:---|
| 1 | 圈选→保存 | 缺按钮 |
| 2 | 指标→申请 | 路径长 |
| 3 | 工单→处理 | 跨模块 |
| 4 | 分析→分享 | 无统一输出 |
| 5 | 收藏→同步 | 我的收藏在 discovery,但探索里看不到 |

### 4.4 一致性(3 个)

| # | 断点 | 表现 |
|:---:|:---|:---|
| 1 | UI 风格 | 不同模块用不同组件库细节 |
| 2 | 命名 | "数据地图" vs "资产目录" vs "资产总览" 同一概念三种叫法 |
| 3 | 交互模式 | 一个按钮在 A 模块是主操作、B 模块是次操作 |

### 4.5 边界认知(3 个)

| # | 断点 | 表现 |
|:---:|:---|:---|
| 1 | 模块入口费解 | "数据探索"和"数据发现"新用户分不清 |
| 2 | 数据归属感 | 在 management 改了字段,discovery 看不到修改 |
| 3 | 跨子应用边界 | dmt-app / mkt-app / touch 是独立系统,数据分散 |

## 5 · 整合建议(按用户旅程 ROI 排序)

### 🔴 P0(立刻可见)

| # | 建议 | 影响旅程 | 投入 |
|:---:|:---|:---:|:---:|
| 1 | **搜索结果按用户意图分类**(而非数据类型),增加"客户洞察"分类 | A | 小 |
| 2 | **跨模块跳转带上下文**(选中项、筛选、时间范围通过 query 传) | A/B/D | 中 |
| 3 | **指标详情 → 申请使用 一键**(避免跳管理) | B | 小 |
| 4 | **圈选 → 保存为标签 一键**(避免跳 tag-system) | C | 中 |
| 5 | **统一"我的产出"** | E | 中 |

### 🟠 P1(季度内)

| # | 建议 | 影响旅程 | 投入 |

| 2 | Owner 统一走共享底座 | B/D | 大 |
| 3 | 字段权限统一入口(customer360 v3.3) | A | 大(独立 PRD) |
| 4 | "数据地图"等命名统一 | 一致性 | 小 |

### 🟢 P2(长期)

| # | 建议 | 影响旅程 | 投入 |
|:---:|:---|:---:|:---:|
| 1 | 概念词典:标签 vs 人群 vs 圈选 | C | 小 |
| 2 | UI 风格统一 | 一致性 | 中 |
| 3 | 子应用边界再设计(dmt/mkt/touch) | E | 大 |

## 6 · 整合前后用户旅程对比

### 旅程 A:看客户授信额度(整合后)

```
1. 登录 → UnifiedWorkbench
2. 搜索"客户授信"
3. → 看到分类:数据表 / 指标 / **客户洞察** / 看板
4. → 点击"客户洞察" → 跳到 /discovery/customer360(预填搜索)
5. → 在 360 列表找到目标客户,看到授信总额
```

**对比整合前**:
- ❌ 之前需要:工作台 → 搜索 → 跳数据地图 → 跳指标 → 跳 360(4 跳)
- ✅ 之后:工作台 → 搜索 → 跳 360(2 跳)

### 旅程 B:申请外数指标(整合后)

```
1. 在 indicator-dashboard 看到外数 X
2. 点详情 → Drawer 显示
3. → Drawer 内有"申请使用"按钮(不跳页)
4. → 提交后,工作台顶部"我的申请"显示进度
5. → 审批通过自动通知
```

**对比整合前**:
- ❌ 之前需要:详情 → 跳数据发现看定义 → 跳数据管理 → 找服务申请 → 填工单 → 跳回(5 跳)
- ✅ 之后:详情 → 申请 → 通知(0 跳)

### 旅程 C:人群圈选 → 标签固化(整合后)

```
1. exploration/audience 圈选完人群
2. → 圈选结果页有"保存为标签"按钮
3. → 弹窗:选标签组 / 命名 / 自动带圈选规则
4. → 保存后,管理端 + 探索端 + 客户 360 都看到该标签
```

**对比整合前**:
- ❌ 之前需要:圈选 → 切模块 → 重新建标签 → 手动配规则(高门槛)
- ✅ 之后:圈选 → 保存为标签(0 门槛)

## 7 · 度量指标(整合效果怎么衡量)

| 指标 | 定义 | 目标值 | 当前值 |
|:---|:---|:---:|:---:|
| **跨模块任务完成步数** | 5 个典型旅程的平均跳转次数 | < 3 | ~5 |
| **搜索结果可执行率** | 搜索后点击结果能完成任务的占比 | > 80% | ~30% |
| **指标 schema 一致率** | 同一指标在三处展示的数字/字段一致率 | 100% | ~40% |
| **Owner 信息一致率** | 同一资产在多模块 Owner 一致率 | 100% | ~50% |
| **新用户上手时间** | 从注册到完成第一个任务 | < 30 min | 未知 |
| **跨模块任务放弃率** | 跨模块任务在中途放弃的比例 | < 10% | 未知 |

## 8 · 总结

### 已落地的整合(代码层)

- ✅ L4 统一工作台
- ✅ L3 跨模块跳转契约
- ✅ L2 工作台搜索
- ✅ L1 Pinia Store + composable 共享

### 仍待解决的断点(用户旅程层)

| 类别 | 数量 | 优先级 |
|:---|:---:|:---:|
| 🔴 上下文丢失 | 5 | P0 |
| 🟠 信息分裂 | 6 | P1 |
| 🟡 操作割裂 | 5 | P0-P1 |
| 🟢 一致性 | 3 | P2 |
| ⚪ 边界认知 | 3 | P2 |

### 核心洞见

> **代码整合只是手段,用户旅程整合才是目的。**
>
> 用户不在乎"我在哪个模块",只在乎"我能多快完成任务"。
> 真正的整合是让用户**忘记模块的存在**。
