# 架构治理路线图

生成时间：2026-06-24

## 1. 路线图目标

本路线图基于以下已有结论整理：

- 当前仓库是“主应用 `src/` + 多子应用 `apps/*` + 少量共享包 `packages/*` + 多套 mock 数据体系”的混合型前端 monorepo
- 当前最大问题不是功能不足，而是边界未收口、子应用类型混杂、mock 方案分裂、共享层不够统一
- 当前治理重点不应是继续拆分新应用，而应先完成分类、收敛、模板化和共享化
- 根目录 `src/` 中存在较多历史实现，后续应逐步迁移并退役，所有业务能力以 `apps/*` 为主承载

这份路线图的核心目标是：

1. 让仓库从“能运行的展示工程”升级为“可持续演进的平台型前端工程”
2. 让 `apps/*` 从“项目集合”收敛为“清晰分层的子应用体系”
3. 让 `mock` 从“多套并存”收敛为“统一治理的前端数据底座”
4. 让根 `src/` 从“历史主应用”演进为“legacy 归档”，由 `apps/main-shell` 统一承接主应用壳职责

## 2. 目标状态

治理完成后，建议仓库收敛到下面的目标状态：

```text
data_community/
├── apps/
│   ├── main-shell            # 主应用壳，负责路由、导航、守卫、子应用挂载
│   ├── risk-app              # 风险域
│   ├── mkt-app               # 营销域
│   ├── dex-app               # 数据探索域
│   ├── touch                 # 触达域
│   ├── admin-app             # 平台管理域
│   └── tools/*               # 工具型应用，如 horizontal-canvas
│
├── packages/
│   ├── shared-api            # 统一请求与接口协议
│   ├── shared-utils          # 公共工具
│   ├── shared-types          # 公共类型
│   ├── shared-constants      # 公共常量
│   ├── shared-mock           # 统一 mock 协议与数据入口
│   └── shared-registry       # 子应用注册协议
│
├── legacy/                   # 迁移中或待归档内容
├── docs/
└── scripts/
```

目标原则：

- 一个业务域只有一个主实现
- 一类子应用只有一种治理口径
- 一套业务只保留一条主 mock 链路
- 一个共享能力只保留一个权威来源

## 3. 当前问题到治理主题映射

| 当前问题 | 治理主题 | 目标结果 |
| --- | --- | --- |
| 主应用过重/历史代码过期 | 主应用退役与壳迁移 | 所有业务归位到 `apps/*`，主壳迁移到 `apps/main-shell`，根 `src/` 进入 legacy |
| 子应用类型混杂 | 子应用分层治理 | 业务子应用、工具应用、后端服务分开治理 |
| 子应用边界重叠 | 业务边界收口 | 每个子应用保留唯一职责 |
| mock 来源分裂 | mock 统一治理 | 统一 mock 接入方案和数据协议 |
| 共享层不足 | 共享层建设 | 类型、常量、协议、mock、API 统一下沉 |
| 工程不一致 | 模板标准化 | 统一入口、路由 base、端口、依赖、目录结构 |

## 4. 治理主线

建议按 6 条主线并行推进：

### 4.1 主线 A：子应用分类治理

目标：

- 把 `apps/*` 里的项目重新分组
- 明确哪些属于标准业务子应用，哪些属于工具型应用，哪些不应继续留在当前口径中

范围：

- 业务子应用：`risk-app`、`mkt-app`、`dex-app`、`touch`、`admin-app`
- 优先收敛对象：`dfd-app`、`dmt-app`、`asset-app`
- 工具型应用：`horizontal-canvas`
- 独立联调项目：`report-monitor`
- 非前端服务：`report-monitor-backend`

### 4.2 主线 B：业务边界收口

目标：

- 消除跨应用重复实现
- 明确子应用唯一职责

当前重点冲突：

- `mkt-app` 与 `touch`
- `dmt-app` 与 `asset-app`
- `dfd-app` 与 `dex-app`
- 根 `src/` 与若干子应用的重复业务实现

### 4.3 主线 C：mock 统一治理

目标：

- 统一 mock 数据来源、接入方式和目录规范
- 降低页面直接 import 业务假数据的比例

建议收敛方向：

- 统一以 `page/store -> api -> mock route` 作为主链路
- 把业务静态数据、接口 mock、测试 mock、工具 mock 分目录管理
- 逐步减少 `Mock.mock` 手工注册、本地 request 分发器、页面直引业务数据等分叉方案

### 4.4 主线 D：共享层建设

目标：

- 把“重复但通用”的能力下沉到 `packages/*`

优先共享对象：

- 类型定义
- 常量与路由协议
- 子应用注册协议
- 统一 API 封装
- mock 协议和通用 mock 数据模型

### 4.5 主线 E：工程模板标准化

目标：

- 为标准业务子应用沉淀一套统一模板

模板最低要求：

- 标准入口 `main.ts`
- 标准路由 `router.ts`
- 标准 `registry.ts`
- 标准 `vite.config.ts`
- 显式依赖声明
- 统一端口配置方式
- 统一 mock 接入方式

### 4.6 主线 F：主应用退役与全子应用化

目标：

- 由 `apps/main-shell` 成为唯一主应用壳
- 所有业务能力与页面以 `apps/*` 为权威来源
- 根目录 `src/` 进入过渡与归档阶段，不再承载新增业务

核心规则：

- 新功能只允许落在 `apps/*`（以及必要的 `packages/*`）
- 根 `src/` 只允许做迁移期兼容与“迁移到 apps 的中转改造”
- 对根 `src/` 的新增页面、模块、mock 增量一律视为治理倒退

## 5. 分阶段路线图

## 第一阶段：止损与分类

周期建议：第 1-2 周

目标：

- 先停止边界继续发散
- 先让仓库可解释、可治理

关键动作：

- 明确 `apps/*` 分类：
  - 标准业务子应用
  - 工具型应用
  - 联调项目
  - 非前端服务
- 明确 `src/` 的定位：
  - 短期作为过渡壳，维持可运行与路由兼容
  - 中期迁移主壳到 `apps/main-shell`
  - 长期将根 `src/` 归档为 `legacy/` 或彻底移除
- 明确“全子应用化”规则：
  - 所有新增业务页面只能落到 `apps/*`
  - 根 `src/` 禁止新增业务模块
- 冻结高风险扩张点：
  - `dfd-app` 暂停新增跨域页面
  - `asset-app` 暂停继续独立扩展
  - `mkt-app` 暂停继续复制 `touch` 能力
- 输出一版仓库分层规则文档

阶段交付物：

- `apps/*` 分类清单
- 子应用治理分组清单
- 仓库分层原则文档

验收标准：

- 每个应用都有明确治理归属
- 团队对“什么是标准子应用”达成一致
- 高风险重复建设点停止继续扩散
- 根 `src/` 被明确标注为过渡/legacy 区域，并建立“禁止新增业务”的约束

## 第二阶段：边界收口

周期建议：第 3-6 周

目标：

- 把最明显的重复和冲突先解决掉

关键动作：

- 收口 `mkt-app` 与 `touch`：
  - 明确触达能力唯一归属
  - 删除营销域里复制的触达页面、service、mock
- 收口 `dmt-app` 与 `asset-app`：
  - 决定 `asset-app` 是并回、重构还是废弃
  - 资产域能力只保留一个主入口
- 收口 `dfd-app` 与 `dex-app`：
  - `dfd-app` 回归数据发现主线
  - 客户 360、事件、工作流等探索能力归位
- 收口根 `src/` 与子应用重复页面：
  - 所有业务页面优先迁移到对应子应用
  - 根 `src/` 只保留迁移期必要的壳能力与兼容跳转

阶段交付物：

- 业务边界矩阵
- 冲突模块清理清单
- 首批重复目录归并结果

验收标准：

- `touch` 与 `mkt-app` 的边界清晰
- `asset-app` 去向明确
- `dfd-app` 职责范围明显收窄
- 根 `src/` 不再新增业务页面，且已开始从根路由移出业务模块

## 第三阶段：模板标准化

周期建议：第 7-10 周

目标：

- 以成熟子应用为样板，建立统一模板

标准样板建议：

- `risk-app`
- `mkt-app`
- `dex-app`

关键动作：

- 统一子应用目录结构
- 统一入口和路由基座
- 统一 `registry.ts` 协议
- 统一端口配置和启动脚本
- 显式声明依赖，禁止依赖 hoist 才能运行
- 收口 `store/stores` 双体系命名问题

阶段交付物：

- 子应用模板规范文档
- 标准业务子应用脚手架结构
- 端口与脚本统一清单

验收标准：

- 新增子应用可以按模板创建
- 样板子应用结构一致
- 启动方式、端口配置、依赖声明一致

## 第四阶段：mock 统一治理

周期建议：第 11-14 周

目标：

- 让 mock 成为统一底座，而不是历史遗留集合

关键动作：

- 统一 mock 分类：
  - 接口 mock
  - 展示型静态数据
  - 测试数据
  - 已废弃 mock
- 优先把页面直接 import 的业务假数据改成：
  - `page/store -> api -> mock route`
- 下线分散方案：
  - 本地 request 路由器
  - 散落在页面里的临时数据
  - 无统一规范的 `Mock.mock` 手工注册
- 建立 `shared-mock` 或统一 mock 协议层

阶段交付物：

- mock 目录与命名规范
- mock 数据索引文档
- 统一 mock 接入样例

验收标准：

- 主业务子应用只有一种主 mock 链路
- 页面直接引业务 mock 的比例显著下降
- mock 来源可追踪、可解释、可替换

## 第五阶段：共享层与主应用收壳

周期建议：第 15-18 周

目标：

- 把平台能力沉到共享层，把主应用收敛成真正的壳

关键动作：

- 建设共享包：
  - `shared-types`
  - `shared-constants`
  - `shared-registry`
  - `shared-mock`
- 把重复类型、菜单协议、路由协议、mock 协议下沉
- 主应用只保留：
  - 登录态
  - 导航与菜单
  - 路由守卫
  - 子应用挂载
  - 公共页面

阶段交付物：

- 新共享包目录
- 主应用壳职责说明
- 共享协议文档

验收标准：

- 主应用不再承载重复业务页面
- 共享能力有明确权威来源
- 子应用不再大面积复制协议、类型、常量
- 根 `src/` 已进入 `legacy/` 或仅保留最小兼容层，主壳能力已由 `apps/main-shell` 承接

## 6. 分组治理策略

### A 组：继续建设型

- `mkt-app`
- `risk-app`
- `dex-app`

路线：

- 先作为样板治理
- 再沉淀模板
- 最后扩展内部模块化

### B 组：优先收敛型

- `touch`
- `admin-app`
- `dmt-app`
- `dfd-app`
- `asset-app`

路线：

- 先明确唯一职责
- 再清理重复
- 最后决定保留、并回或降级

### C 组：单独治理型

- `horizontal-canvas`
- `report-monitor`
- `report-monitor-backend`

路线：

- 不纳入标准业务子应用模板
- 单独制定工具型和联调型项目规范

## 8. 成功指标

建议用下面的指标评估治理效果：

### 结构指标

- 标准业务子应用占比提升
- 缺失入口/路由异常/配置漂移的应用数下降
- 重复业务目录数下降

### 工程指标

- 端口配置冲突数下降
- 隐式依赖数量下降
- 启动脚本和运行方式一致性提升

### 数据指标

- 页面直接 import 业务 mock 的数量下降
- 统一 mock 链路覆盖率提升
- mock 数据来源可追踪率提升

### 架构指标

- 根 `src/` 中的重复业务页面数下降
- 共享包被实际消费的数量提升
- 子应用边界冲突点数量下降

## 9. 风险与应对

| 风险 | 说明 | 应对策略 |
| --- | --- | --- |
| 治理期间影响演示 | 项目承担展示用途，不能大面积中断 | 采用“冻结扩张 + 小步收口”策略 |
| 边界争议大 | 不同成员对业务归属理解不同 | 先做职责矩阵，再动代码 |
| mock 改造成本高 | 页面直引假数据太多 | 先治理主链路，不追求一次性全部清理 |
| 样板无法统一 | 子应用成熟度差异大 | 只以 `risk-app`、`mkt-app`、`dex-app` 先沉淀样板 |
| 工具项目被误伤 | `horizontal-canvas`、`report-monitor` 不适合统一模板 | 分组治理，不一刀切 |

## 10. 推荐推进顺序

如果只按最务实的顺序推进，建议这样做：

1. 先分类：厘清项目类型和治理口径
2. 再止损：冻结高风险扩张点
3. 再收口：优先解决 `mkt-app/touch`、`dmt-app/asset-app`、`dfd-app/dex-app`
4. 再模板化：以 `risk-app`、`mkt-app`、`dex-app` 建标准模板
5. 最后共享化：统一 mock、协议、类型和主应用壳

## 11. 结论

当前项目已经具备成为“平台型前端工程”的基础，但前提不是继续增加页面和子应用，而是先完成治理收口。

这条路线图的核心逻辑是：

- 先分类
- 再收口
- 再标准化
- 再共享化
- 最后稳定扩展

如果按这个顺序推进，仓库会从“多项目并存的展示工程”，逐步走向“边界稳定、模板统一、可持续演进的前端平台”。
