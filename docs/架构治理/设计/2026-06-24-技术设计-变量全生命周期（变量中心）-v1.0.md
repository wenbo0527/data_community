# 技术设计文档：变量全生命周期（变量中心）v1.0

生成时间：2026-06-24

## 1. 背景与决策

### 1.1 背景

“变量全生命周期/变量一体化管理”是一个以变量资产为核心的管理能力，主要使用方是：

- 风险数据团队：变量衍生、评估、陪跑、上线、运营、下线的全流程管理
- 数据应用团队：变量复用、运营监控、效果评估、版本与口径追踪

同时，变量的资产结果需要在以下域被消费与展示：

- 数据发现：统一搜索、元数据详情、血缘追踪、资产推荐
- 数据管理：资产登记、标准与口径、权限与上架下架治理
- 数据探索：分析验证与应用验证
- 营销：策略/人群/触达/画布等引用变量资产

### 1.2 能力归属（产品域）

最终能力归属选择为：数据管理域（DMT）。

原则：

- 变量中心是平台级资产能力，必须有单一权威源
- 风险域、探索域、营销域是消费方与场景入口，不应各自维护生命周期状态机

### 1.3 与交互设计文档的关系

交互设计文档地址：

- `docs/需求文档/2026-06-24-交互设计-变量一体化管理方案-v1.0.md`

本技术设计仅补齐实现视角的关键决策：

- 子应用归属与路由落点
- 模块边界与能力拆分
- 跨域复用策略（dfd-app、OA）
- mock 数据体系与数据同步模型
- 迁移与治理约束（避免根 src 与多 app 分叉）

## 2. 范围（Scope）

### 2.1 P0 范围

以交互设计文档 P0 为准，包含变量生命周期的核心链路：

- 变量管理工作台
- 变量列表
- 变量档案（详情页/报告页/血缘页/生命周期档案页）
- 变量注册/编辑
- 批量导入
- 变量市场
- 数据源管理（外数/征信/内数入口 + 内数底表注册）
- 流程中心（OA 工单嵌入）
- 统一搜索/元数据详情/血缘（嵌入 dfd-app）

### 2.2 非目标（Non-goals）

- 不实现真实后端与真实鉴权体系
- 不实现真实数据计算与调度
- 不做移动端适配
- 不在 P0 阶段实现“微前端同页挂载”，优先采用跳转/iframe 方式达成演示闭环

## 3. 总体架构与应用划分

### 3.1 子应用划分

在“全子应用化 + 主应用退役”治理方向下，变量中心建议落到 `apps/dmt-app` 体系内，作为数据管理域的核心模块。

建议的长期结构：

```text
apps/
  main-shell/                 主壳（目标）
  dmt-app/                    数据管理域（变量中心权威源）
    pages/variable-management 变量中心主模块
  dfd-app/                    数据发现域（提供搜索/元数据/血缘能力）
  risk-app/                   风险域（场景入口，复用外数生命周期/评估能力）
  mkt-app/                    营销域（消费方）
  dex-app/                    探索域（消费方）
packages/
  shared-api/                 请求封装
  shared-mock/                变量资产 mock 与协议（建议新增）
  shared-types/               变量资产模型类型（建议新增）
```

说明：

- 现阶段仓库里变量相关实现分散在根 `src`、`dmt-app`、`asset-app` 等处，必须以“权威源归属”为约束收口到 `dmt-app`
- 风险域是“主要使用场景”，但不应成为权威资产源；风险域只提供入口与复用能力（外数评估、外数档案等）

### 3.2 系统上下游关系

```text
变量中心（权威源，dmt-app）
  |
  +-- 发布 VariableAsset（变量资产视图，含状态/版本/口径/元数据关联/索引）
  |
  +-- 被以下系统消费：
        dfd-app：搜索/元数据/血缘（被嵌入 + 资产索引消费）
        risk-app：入口与复用（外数生命周期/评估）
        dex-app：分析验证消费
        mkt-app：策略与运营消费

流程与留痕：
  Feishu OA：工单与审批（嵌入）
```

## 5. 领域模型与数据同步

### 5.1 权威数据对象：VariableAsset

变量中心对外发布的权威视图建议统一为 `VariableAsset`（可理解为“变量资产表”），由变量中心维护并同步给消费域。

建议字段（P0 最小集合）：

| 字段 | 含义 |
| --- | --- |
| `id` | 变量唯一标识 |
| `name` | 变量名称 |
| `code` | 变量编码（可选） |
| `domain` | 业务域（risk/marketing/…） |
| `owner` | 负责人/团队 |
| `status` | 生命周期状态（草稿/评估中/陪跑中/运营中/已暂停/待下线/已下线） |
| `version` | 当前版本 |
| `definition` | 口径摘要（文本/JSON） |
| `sourceType` | 外数/征信/内数 |
| `sourceRefs` | 数据源引用（按 sourceType 关联外数/征信/内数资产 id） |
| `metadataRefs` | 关联元数据（表/字段/指标 id 列表） |
| `lineageRef` | 血缘定位参数（dfd-app 可识别的 variableId 或节点 id） |
| `lastUpdatedAt` | 最近更新时间 |

### 5.2 同步拆分：主数据 / 索引 / 摘要

建议把同步对象拆成三层：

1. 资产主数据：`VariableAsset`（必须同步）
2. 关系与索引：元数据关联、血缘定位参数（强烈建议同步）
3. 运行结果摘要：评估指标摘要、预警摘要（按需同步）

消费方使用原则：

- dfd-app：只消费索引与定位参数，用于搜索与血缘联动
- dmt-app：权威源
- risk/mkt/dex：只读消费变量资产，不维护生命周期状态机

## 6. 跨域复用与嵌入策略

### 6.1 dfd-app 复用

复用能力：

- 统一搜索
- 元数据详情
- 血缘分析

嵌入策略（P0 推荐）：

- iframe 方式嵌入 dfd-app 页面或组件容器

升级策略（P2 可选）：

- 微前端方式嵌入，统一路由与参数协议

最小参数协议（建议）：

- 血缘页支持：`?variable=<variableId>` 自动定位当前变量
- 元数据详情支持：`/metadata/:id` 与 `:id` 统一为 dfd-app 内部可识别 id

### 6.2 Feishu OA 复用

复用能力：

- 工单创建、审批、留痕

嵌入策略：

- P0：iframe 嵌入 OA 工单详情页 + 新标签页打开创建工单
- URL 参数：携带 `variableId`、`variableName` 等用于 OA 侧展示与回跳

### 6.3 与外数生命周期（risk-app）打通

变量与外数生命周期的关系，本质是“变量资产的 sourceType=外数 时，需要对外数资产形成可追踪引用，并复用外数域的既有页面/报告能力”。

#### 6.3.1 关联模型（建议）

当 `sourceType = 外数` 时，`sourceRefs` 推荐承载以下引用之一或组合：

| 引用类型 | 字段建议 | 对应 risk-app 资产/页面 |
| --- | --- | --- |
| 外数服务 | `externalServiceId` | `/risk/external-data/service`（列表） |
| 外数档案 | `externalArchiveId` | `/risk/external-data/archive/:id` |
| 外数评估 | `externalEvaluationId` | `/risk/external-data/evaluation/:id` |
| 外数生命周期实例 | `externalLifecycleId` | `/risk/external-data/lifecycle/:id` |

说明：

- P0 不要求把 risk-app 的内部数据模型“搬到变量中心”，只要建立稳定的“引用关系”即可
- 变量中心只维护“引用关系 + 摘要信息”（例如供应商、产品、接口、评估结论摘要），详情展示复用 risk-app 页面

#### 6.3.2 交互打通（推荐）

变量中心（dmt-app）在以下位置提供跳转：

- 变量详情页 Tab1“数据源”区域：展示外数引用摘要 + “查看外数档案/评估/服务”按钮
- 数据源列表（外数 Tab）：直接跳转到 risk-app 的外数相关列表页

跳转方式（P0 推荐）：

- 使用深链跳转到 risk-app 对应路由
- 深链使用 `routerBase=/risk/` 约定，路径形如：`/risk/external-data/archive/:id`

#### 6.3.3 数据一致性（在纯 mock 约束下的做法）

由于当前项目以 mock 为主，建议用“单一数据源 + 多视图派生”的方式避免口径分裂：

- 变量中心维护 `VariableAsset`（权威源）
- 外数生命周期维护 `ExternalDataAsset`（权威源，仍在 risk-app 内）
- 在 `shared-mock`（或 dmt-app mock）中建立“映射表”：
  - `variableId -> externalArchiveId/externalEvaluationId/...`

P0 阶段只需要保证：

- 跳转 id 可用（能打开对应页面）
- 变量详情中展示的摘要字段与 risk-app 页面展示不明显矛盾

#### 6.3.4 后续演进（P1/P2）

- P1：把外数评估报告组件抽成可复用模块（或通过 iframe/微前端嵌入 risk-app 的评估详情页）
- P2：如果需要“同页联动”，再升级为微前端嵌入方案，并定义更严格的参数协议（如 `?variableId=...&externalArchiveId=...`）

## 7. Mock 方案（本项目约束）

### 7.1 原则

- 变量中心作为权威源，mock 数据也必须以变量中心为权威来源
- 消费域不得各自维护独立 mock 数据口径

### 7.2 推荐落地方式

P0 推荐使用统一 HTTP mock 主链路：

- `page/store -> api -> mock route`

建议新增：

- `packages/shared-mock/variable`：变量资产的 mock 数据源与生成器
- `packages/shared-types/variable`：变量资产类型定义

如果暂不新增包：

- 先在 `apps/dmt-app/src/mock/variable-management/*` 集中维护，并逐步迁移到 shared-mock

## 8. 与现有仓库实现的关系（治理约束）

### 8.1 现状问题

当前仓库存在变量相关实现多处并存（根 `src`、`dmt-app`、`asset-app` 等），会导致：

- 生命周期状态机多份实现
- mock 数据口径多份来源
- 菜单与路由分叉

### 8.2 收口策略

规则：

- 变量生命周期相关页面的唯一权威实现：`apps/dmt-app`
- 根 `src` 的变量路由仅保留为兼容跳转或迁移期入口，禁止新增业务能力

迁移建议：

- 第一步：冻结根 `src` 的变量相关增量
- 第二步：在 `dmt-app` 内对齐路由与页面结构到交互设计版本
- 第三步：在主壳层统一入口，逐步把用户流量迁移到 `dmt-app`
- 第四步：归档根 `src` 的旧实现到 `legacy`

## 9. 分工建议（1 人 + 多 Agent）

建议按“权威源优先”分工：

- 架构与治理（你）：确定权威归属、同步模型、路由归位规则、shared 包策略
- 实现 Agent（执行）：优先在 `apps/dmt-app` 完成变量中心页面与 mock
- 复用对接 Agent（执行）：dfd-app 嵌入参数协议、OA 跳转协议
- 审核 Agent：检查是否出现新的重复实现与 mock 分叉

## 10. 验收清单（P0）

### 10.1 体验闭环

- 工作台 → 列表 → 档案（详情/报告/血缘/档案）链路可用
- 新建/编辑/导入可演示
- 流程中心可打开 OA 并回跳到变量详情

### 10.2 复用正确性

- 血缘页可按 `variableId` 定位（dfd-app 参数协议）
- 统一搜索/元数据详情/血缘嵌入稳定

### 10.3 架构约束

- 变量生命周期状态机只有一处权威实现
- mock 数据口径只有一处权威来源
- 根 `src` 不再新增变量相关页面与 mock
